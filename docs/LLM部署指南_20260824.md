# 赛道 C LLM 部署指南（步骤③④：模型转换 + llama.cpp 部署）

> 日期：2026-08-24 ｜ 配套教程：`docs/LLM微调手把手教程_20260824.md`
> 依赖产物：LoRA 适配器 `models/llm/qwen-traffic-v1/`（步骤②产出）

## 1. 转换链路总览

```
LoRA 适配器 + 基座模型
   │ ① merge 合并（peft → 完整 HF 权重）
   ▼
models/llm/gguf/qwen-traffic-merged/（HF 格式，~1GB）
   │ ② convert_hf_to_gguf.py 导出
   ▼
models/llm/gguf/qwen-traffic-f16.gguf（F16，~1GB）
   │ ③ llama-quantize Q4_K_M 量化
   ▼
models/llm/gguf/qwen-traffic-q4_k_m.gguf（INT4，~350MB）★ 部署产物
```

工具位置：`tools/llama.cpp/`（llama-server.exe、llama-quantize.exe、convert_hf_to_gguf.py + conversion/ 包）。

## 2. 合并 LoRA（在模型训练机执行）

```python
# llm_train/merge.py（已入库）
python -m llm_train.merge --adapter models/llm/qwen-traffic-v1 \
    --base models/llm/base/qwen2.5-0.5b-instruct \
    --out models/llm/gguf/qwen-traffic-merged
```

## 3. 导出 GGUF + 量化对比

```bash
# F16 导出（需 gguf 包；本机用 tools/llama.cpp/gguf_patch_convert.py 补架构枚举）
python tools/llama.cpp/gguf_patch_convert.py models/llm/gguf/qwen-traffic-merged \
    --outfile models/llm/gguf/qwen-traffic-f16.gguf --outtype f16

# 正式部署模型：f32（精度验证后唯一可用档位，见第 6 节量化结论）
python tools/llama.cpp/gguf_patch_convert.py models/llm/gguf/qwen-traffic-merged \
    --outfile models/llm/gguf/qwen-traffic-f32.gguf --outtype f32

# 对比用：INT4/INT6 量化（tools/llama.cpp/llama-quantize.exe，b10612 版）
llama-quantize.exe qwen-traffic-f16.gguf qwen-traffic-q4_k_m.gguf Q4_K_M
llama-quantize.exe qwen-traffic-f16.gguf qwen-traffic-q6_k.gguf Q6_K
```

## 4. 启动 llama-server（云脑推理服务）

Windows 本地进程（正式部署配置，2026-08-24 验证）：

```bash
tools/llama.cpp/llama-server.exe \
    -m models/llm/gguf/qwen-traffic-f32.gguf \
    --host 127.0.0.1 --port 8081 \
    --n-gpu-layers 99 -c 2048 --alias qwen-traffic --repeat-penalty 1.0
```

- `--alias qwen-traffic`：模型别名，与 `server/llm_service.py` 的 `LLM_MODEL` 默认值对应
- 验证：`curl http://127.0.0.1:8081/v1/models`
- OpenAI 兼容：`POST /v1/chat/completions`（llm_service 直接调用，**不加 system 消息**）

## 5. 接入 API 网关

`POST /api/v1/llm/analyze`（server/api_server.py 新增，错误码规范与现有接口一致）：

```json
// 请求：交通状态窗口文本（llm_data.text_format.format_window_text 渲染）
{"text": "【场景】早高峰…【路口 J16】最近 30 秒交通状态…", "junction": "J16"}

// 响应
{
  "api_version": "v1",
  "junction": "J16",
  "event": "拥堵", "event_en": "congestion",
  "confidence": 0.92,
  "advice": "北向排队12辆…建议优先切换至放行北向的相位。",
  "latency_ms": 180.5,
  "llm_backend": "llama.cpp", "llm_model": "qwen-traffic"
}
```

错误码：`LLM_SERVICE_UNAVAILABLE`(503，llama-server 未启动)、`LLM_PARSE_FAILED`(502，输出非 JSON)、`LLM_INVALID_EVENT`(422，事件值非法)。

环境变量：`LLM_BASE_URL`（默认 `http://127.0.0.1:8081/v1`）、`LLM_MODEL`（默认 `qwen-traffic`）。

## 6. 精度/体积/延迟对比表（2026-08-24 实测，100 条均衡 val 样本）

| 模型形态 | 体积 | 事件准确率 | 正常/拥堵/溢出/事件召回 | 单条延迟（GPU） |
|---------|------|-----------|------------------------|----------------|
| 基座 bf16（微调前） | ~1GB | 25.0% | 100/0/0/0（只会说正常） | — |
| 微调后 bf16（HF 推理） | ~1GB | 99.5% | 100/98/100/100 | ~6.1s（transformers） |
| **微调后 f32 GGUF（正式部署）** | **1.98GB** | **100.0%** | **100/100/100/100** | **~5.0s（P95 6.2s）** |
| 微调后 Q6_K GGUF | 506MB | 66.0% | 100/84/76/4 | ~3.2s |
| 微调后 Q4_K_M GGUF | 379MB | 62.0% | 100/68/80/0 | ~3.2s |

### 量化适用性结论（重要，答辩素材）

**INT4/INT6/INT8 量化在本任务上不可用**：0.5B 小模型的决策边界对计算精度敏感——
"事件"类依赖"低均速"等精细数值信号，量化后事件召回从 100% 掉到 0-4%。
f16 计算（llama.cpp 默认）同样损失精度（66%），必须 f32 计算。

这是**有价值的负面发现**：轻量化不是"无脑量化"，量化必须逐任务验证精度——
本任务最终部署 f32 GGUF（1.98GB），对比通用 7B 模型（14GB+，Q4 后仍 4.5GB）
依然是 1/7 体积；同时保留 Q4（379MB）作为"最小体积可用性"讨论素材。

### 推理配置要点（本机踩坑记录）

1. **必须 --n-gpu-layers 99 + f32 模型**：f16 模型/计算会丢失事件判别精度；
2. **不要加 system 消息**：微调数据只有 user+assistant 两段，llm_service 不加 system
   （实测加 system 后事件召回掉到 ~0%）；用户文本自带【问题】指令；
3. **--repeat-penalty 1.0**：JSON 输出大量重复结构，默认 1.1 惩罚会干扰；
4. 延迟 ~5s/条 = 云脑慢周期分析（每 2-5 分钟一次），实时控制仍由 DQN 边缘模型承担。
