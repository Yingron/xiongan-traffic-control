## 1. 绪论：项目背景与国内外研究现状

### 1.1 研究背景与赛题需求

- **雄安新区背景**：作为国家智慧城市建设的"未来之城"，以"窄路密网"为特色城市肌理（路口间距短、路网密度高、机非混行频繁），传统定时信号控制难以实现系统级最优；"车"的智能与"城"的智慧之间缺乏 AI 驱动的协同"大脑"。
- **车路云一体化**：通过 AI 算法将分散的车辆、路侧设施连接为可自主学习、协同进化的城市级智能系统（题目背景表述）。
- **赛题三大功能需求**（XH-202613）：
  - 功能一：智能交通协同管控算法的抽象设计与建模（场景建模、接口设计、控制策略实现与验证、AI 决策模型）；
  - 功能二：高保真仿真验证平台通用性架构搭建（≥20 路口路网、数据采集与可视化、算法接入适配器、容器化部署）；
  - 功能三：赛道 C（AI 应用型）——AI 模型轻量化部署验证（数据处理、训练/微调、模型转换、部署全流程）。
  - 映射到报告章节：功能一 → 2.6（算法理论设计）+ 2.4（接口契约）+ 3.1（实现细节）；功能二 → 3.3（仿真环境）+ 2.5（可视化）+ 3.2.2（容器化）；功能三 → 3.2（轻量化与云-边-端部署）。
- **政策与产业背景**：2024 年 7 月工信部等五部门公布首批 20 个"车路云一体化"应用试点城市，我国智能网联汽车从单车智能迈向"车路云一体化"规模应用新阶段；无锡已完成 1723 个路口信号灯联网联控，深圳、德清等城市落地云控平台与数字孪生应用。
- **图表建议**：雄安新区"窄路密网"特征示意图；赛题需求-项目功能映射表。

### 1.2 国内外研究现状调研

> 本节约 3~4 页，按四个方向综述**国内外**代表性工作（每个方向先国外再国内），末节给出对比与差距，引出本项目定位。参考文献按 GB/T 7714 整理（清单见文末）。

#### 1.2.1 自适应交通信号控制与强化学习方法

- **传统自适应控制（国际）**：SCATS（澳大利亚悉尼协调自适应交通系统）、SCOOT（英国分裂-周期-偏移优化技术）在全球与国内城市的引进、本地化与应用效果。
- **深度强化学习基础（国际）**：DQN 开创性工作（Mnih 等，Nature 2015）；单路口/多路口 DRL 信号控制的状态-动作-奖励建模框架。
- **多智能体强化学习（国际）**：VDN、QMIX 等值分解方法为区域级信号协同提供训练范式（CTDE）。
- **国内综述**：
  - 徐东伟等，《基于深度强化学习的城市交通信号控制综述》，《交通运输工程与信息学报》2022, 20(1): 15–30；
  - 华贇、王祥丰、金博，《面向城市交通信号优化的多智能体强化学习综述》，《运筹学学报》2023, 27(2): 49–62；
  - 于泽等，《深度强化学习驱动的智能交通信号控制策略综述》，《计算机科学》2023, 50(4): 159–171；
  - 翟子洋等，《大规模智慧交通信号控制中的强化学习和深度强化学习方法综述》，《计算机应用研究》2024, 41(6): 1618–1627；
  - 李泽萱等，《智能体强化学习在智慧交通信号灯中应用综述》，《价值工程》2025。
- **国内代表性算法**：CoLight（图注意力网络建模路口间协同，CIKM 2019，清华）；FRAP（学习相位竞争关系，CIKM 2019）；PressLight/MPLight（压力驱动强化学习，KDD 2019）；离线强化学习与时空图协同等 2025 年新方向。
- **趋势小结**：从单路口/干道优化走向区域与路网级协同；MARL 是解决大规模信号协同的主流路线；车路协同环境下信号-车辆联合控制成为新热点。

#### 1.2.2 车路云一体化与城市级协同管控

- **国际**：C-V2X/车路协同示范区建设；欧洲 C-ITS 部署与云控平台研究；"云-边-端"分层计算架构在智能交通中的探索。
- **国内政策与试点**：2024 年五部门 20 城"车路云一体化"应用试点；2025 年经济日报等报道的试点成效（无锡路口联网联控、深圳交通信息汇聚平台与"申报即更新"机制、德清数字孪生云控平台、广州南沙/深圳坪山示范区）。
- **雄安实践**：雄安新区数字道路建设、"窄路密网"规划理念；河北省智能网联汽车标准化技术委员会牵头的地方标准预研。
- **趋势小结**：车路云一体化从基础设施试点走向规模化应用，但纯云端集中控制面临通信延迟与单点风险、纯车端分布式决策难保全局最优——**云-边-端混合决策框架**是产业界共识方向，公开的算法级验证仍少。

#### 1.2.3 大语言模型在智能交通中的应用

- **国际**：LLMLight/LightGPT（首个将 LLM 直接作为信号控制决策智能体的工作）；Traffic-R1（3B 参数信号控制基础模型）；MARLATS（MCP + ReAct 智能体）；GPTTC（LLM 处理偏移左转交叉口）等。
- **国内**：HeraldLight（双 LLM 架构，LLM-Agent 决策 + LLM-Critic 纠错抑制幻觉，ICPADS 2025，北邮）；苏州"羲和巡路"大模型（2025 年报道）：基于大模型 + 标准化联控技术对姑苏区 422 个信控路口分区建模，双向绿波覆盖率 71.09%，赛事散场 20 分钟清空核心道路——国内大模型信号控制的落地范例。
- **趋势小结**：LLM 从"辅助工具（策略推荐、场景理解）"向"直接决策智能体"演进，并常与 RL 形成 actor-critic 或双 LLM 纠错架构；但直接决策存在延迟高、幻觉风险、可解释性要求严苛等落地障碍，**"边缘实时控制 + 云端慢周期决策支持"的分层方案**尚少被系统验证——本项目即填补此空白。

#### 1.2.4 交通仿真平台与模型轻量化部署

- **仿真平台（国际）**：SUMO（德国宇航中心开源、可编程、TraCI 在线控制）、PTV Vissim（商业仿真）；**（国内）**：CityFlow（清华开源）、数字孪生仿真平台的兴起。
- **轻量化部署**：模型压缩（量化/剪枝/蒸馏）、ONNX 跨框架部署、边缘计算设备（车规级芯片算力约束）下的推理优化；小模型上量化的适用性边界（本项目实测 INT4/INT6/INT8 破坏精细判别，见 3.2 节）。
- **趋势小结**：仿真-算法-部署链路打通是解决"算法在理想路网表现好、真实部署失效"问题的关键；轻量化手段必须针对具体任务实测验证，不能无脑压缩。

### 1.3 现状评述、待解决挑战与对比分析

- **与现有方法的对比（增强可信度）**——按四个维度对比本项目与现有代表性工作的差异：

| 维度 | 现有代表性工作 | 本项目方案 | 差异点 |
|------|---------------|-----------|--------|
| 场景真实性 | 理想/通用路网，同构路口假设 | 30 路口真实路网，5 种信号模板（A–E）实测存在，真实 OD 与配时 | 拓扑异构性显式建模并治理 |
| 协同机制 | 全局单智能体（维度灾难）或 CTDE（训练复杂） | 参数共享 DQN + 需求门控动作掩码 + 模板分层采样 | 以轻量手段解决共享策略在异构拓扑上的锁死问题 |
| 部署验证 | 多停留在算法仿真层 | ONNX 25 KB + 真实状态动作一致率 100% + Docker 容器化 | 以"真实状态保真"而非离线指标作为部署门槛 |
| 云端增强 | LLM 直接决策（延迟/幻觉风险） | DQN 边缘毫秒级控制 + LLM 云端慢周期决策支持 | 规避 LLM 实时控制风险的分层双模型 |

- **由此引入本项目要解决的三大挑战**：
  1. **场景真实性挑战**：如何在"窄路密网"、拓扑异构（5 种相位模板）、多时段需求差异下构建高保真可编程仿真场景（对应功能二）；
  2. **协同落地挑战**：如何设计轻量、可扩展、不锁死相位的多路口协同算法，并在 <1 MB、<5 ms 约束下保真部署到边缘（对应功能一、赛道 C）；
  3. **评估标准化挑战**：如何建立与真实基线同口径的对比实验与指标集（Mobility/Environment/Safety），为《协同管控系统测试规程》提供参考（对应赛题评估要求）。
- **可信度原则**：本项目所有结论基于仓库内可定位的配置、模型、日志与验证报告；失败案例与负面发现（offpeak 病态训练、平峰 −1.6%、INT8 量化不可用、LLM 量化破坏召回）如实呈现，不以理想数据替代实测。

### 1.4 问题定义与工程目标

- 控制对象：30 个有信号控制路口 `J01`–`J30`（6×5 网格，见 3.3 节）；每个控制周期为每路口选择 4 类相位之一（南北直行、南北左转、东西直行、东西左转）。
- 核心挑战：路口间距短导致的排队溢出连锁、拓扑模板差异、早/平/晚高峰需求差异、车规级部署约束。
- 工程目标表（可验收定义）：

| 目标 | 可验收定义 | 当前状态 |
|------|-----------|---------|
| 路网规模 ≥ 20 路口 | SUMO 与 Unity 均识别 J01–J30 | ✅ 30 路口 |
| 状态契约 | 660 维 `v1-30x22` 公开状态 | ✅ 稳定 |
| 决策约束 | 30×4 动作，需求门控掩码禁止无需求相位 | ✅ 26 维观测契约 |
| 模型体积 < 1 MB | FP32 ONNX 25.14 KB | ✅ 已达标 |
| 推理延迟 < 5 ms | 单路口 0.022 ms / 30 路口批量 0.029 ms | ✅ 已达标 |
| 演示闭环 | Unity 三场景切换、信号灯/车辆/指标可追溯 | ✅ 已验收 |

## 2. 系统总体架构、算法设计与创新点

> 本章回答"技术路线怎么走、整体怎么搭、算法理论是什么、创新在哪"。算法理论（选型/原理/建模/掩码机制）在本章完结；工程实现细节在第 3 章展开。创新点前置呈现，让评委在读完本章后即看到差异化贡献。

### 2.1 技术路线总览

- 技术路线五段式：**数据与场景（SUMO + 真实配时/OD）→ 算法（共享掩码 DQN + 需求门控）→ 工程化（ONNX 轻量化 + Docker + Unity 可视化）→ 验证（三场景同口径对比 + 轻量化验收）→ 云端增强（LLM 云脑）**，每段一句话说明内容与对应章节。
- 架构原则（"仿真真值唯一"）：SUMO/TraCI 负责交通演化和信号执行；API 服务负责会话、状态、约束和接口契约；共享 DQN 或 ONNX 边缘模型负责动作选择；Unity 仅通过 WebSocket 接收快照并渲染，不参与训练与决策，避免把视觉状态误用于训练或控制。

### 2.3 一次控制周期与数据流

- 一次控制周期 5 步描述：场景选择 → 状态提取（660 维）→ 掩码计算（30×4）→ ONNX 批量推理（30 动作）→ 安全校验与批量执行 → 广播快照。
- 30 路口动作必须同一仿真时刻批量校验、批量下发（避免逐路口推进造成"同一帧内不同路口读取到不同仿真时刻"的不一致）。

### 2.4 接口契约设计

- **写作要求：纯文字说明，不得出现端点/方法表述（如 GET /xxx、POST /xxx），完整端点明细统一放附录 B。**

### 2.6 协同管控算法设计（理论）

> 对应功能一"智能交通协同管控算法的抽象设计与建模"。纯理论部分（选型 → 原理 → 建模 → 设计）在本节完结；实现细节与训练流程在第 3.1 节。

#### 2.6.1 多智能体策略选型分析

- 三种策略对比：全局单智能体（660 维输入/120 维联合动作）、独立 DQN IQL（22 维/4 动作）、CTDE（QMIX/VDN，训练全局/执行局部）。
- 四维评估（训练效率、可扩展性、通信开销、溢出协同、推理延迟）→ **选型结论：参数共享 DQN**（独立 DQN 训练范式 + 共享网络与经验池），核心理由：训练效率高、可扩展、通信开销低、推理延迟低。
- **图表建议**：三种策略架构对比示意图。

#### 2.6.2 DQN 算法核心原理

- Q 学习基础：Bellman 方程、Q 值更新、γ 折扣因子。
- DQN 关键技术：经验回放（打破样本相关性）、目标网络（稳定 TD 目标）、ε-贪婪探索；本项目进一步采用 **Double-DQN**（缓解过估计，正式模型契约 `shared-dqn-26x4-v1`）。
- 带掩码的 TD 目标（本项目公式）：
  \[
  y = r + \gamma (1-d)\max_{a' \in \mathcal{A}(s')} Q_{\theta^-}(s',a')
  \]
  其中 \(\mathcal{A}(s')\) 为需求门控掩码给出的合法动作集；优化目标 \(\mathcal{L}(\theta)=\mathbb{E}[(y-Q_\theta(s,a))^2]\)。
- **图表建议**：DQN 算法结构示意图（含掩码分支）。

#### 2.6.3 状态-动作-奖励设计

- 状态空间：30 路口 × 22 维 = 660 维（`v1-30x22`）：

| 局部索引 | 特征 | 维度 | 归一化/编码 |
|---:|---:|---:|---|
| 0–3 | N/S/E/W 排队长度 | 4 | min(queue/15, 1) |
| 4–7 | N/S/E/W 平均等待 | 4 | min(wait/120, 1) |
| 8–11 | N/S/E/W 车道占有率 | 4 | [0,1] 原值 |
| 12–15 | N/S/E/W 溢出风险 | 4 | min(queue/15, 1) |
| 16–19 | 当前相位 | 4 | One-Hot |
| 20–21 | 时段特征 | 2 | sin/cos 周期编码 |

  - 设计考量：溢出风险特征针对窄路密网"超容"风险；sin/cos 编码解决 23 点与 0 点不连续；相位 One-Hot 让模型感知时序。
  - 观测组装：660 维拆为 30 个局部状态，各附加 4 位动作掩码 → 26 维输入（掩码为 0 的相位不参与 argmax）。
- 动作空间：4 相位（NS_Straight / NS_Left / EW_Straight / EW_Left），安全约束最小绿灯 15 s + 黄灯 3 s。
- 奖励函数（实现版本号 v3，文档历史名"V5/V5.1"，撰写时以运行时输出为准）：
  \[
  r = -\left(0.8\overline q + 0.6 q_{max} + 0.4 \overline w + 2.0 p_{overflow} + 0.01 c_{switch} + 0.1 p_{balance} + 0.08 p_{stag}\right) + 0.5 r_{queue} + 2.0 n_{crossed} + 0.3 r_{wait}
  \]
  - 吞吐驱动项：队列减少量（通过车辆数代理，权重 2.0）与总等待减少的正向奖励——让智能体学会"放行更多车辆"而非仅"不扣分"；
  - 溢出惩罚高权重（2.0）：针对窄路密网排队回堵风险；切换成本低权重：避免过度惩罚正常相位更替；
  - 每个路口独立计算奖励，全局奖励仅用于监控。
- **图表建议**：22 维特征结构图、奖励函数分量权重图。

#### 2.6.4 参数共享与需求门控掩码设计

- 参数共享：30 路口共享一套 DQN 参数与经验回放池，网络结构固定（输入 26 → 64×64 MLP → 4），新增路口无需改网络；不同拓扑模板与场景经验共同更新同一策略。
- 模板分层采样：按模板加权采样训练路口（A 0.45 / B 0.15 / C 0.20 / D 0.10 / E 0.10，少数模板合计 ≥ 30%），避免模板 A（20/30）垄断梯度；模板 C 双倍加权（已证实的失败模板）。
- 需求门控动作掩码（本项目核心创新）：
  - 相位服务链路无排队需求（halting < 阈值 1）时该动作无效，掩码以最后 4 维追加进观测（22 → 26 维，公开 660 维契约不变）；
  - 动机：共享策略在无掩码时会把 action_0/3 学成"高价值直行相位"，在模板 C 上 90% 时间误选全红相位、1M 训练后坍缩迁移到模板 A 造成全网死锁；需求门控打断"空相位锁定"的自我强化循环；
  - 兜底：全部相位无需求时掩码全 1，避免死锁。
- 溢出协同机制：奖励溢出惩罚 + 共享经验回放（间接协同）+ 可选邻居状态增强（30 维，列为未来工作）。
- **图表建议**：掩码计算流程图、模板分布与采样权重图、掩码前后动作分布对比图。

### 2.7 创新点与技术亮点

**只保留三点（最重点，与 1.3 对比表的三个差异行呼应）：**

1. **需求门控动作掩码：以轻量机制根治异构拓扑下的相位锁死。** 路网实测存在 5 种相位模板，共享参数策略若不加以约束，会把少数模板的动作学成"高价值直行相位"（模板 C 上 90% 时间误选全红相位），并最终坍缩为全网死锁。本方案按各相位服务链路的当前需求动态生成绝对动作掩码，直接打断"空相位锁定"的自我强化循环——全流程收益最大的单一改进（reward 提升 10% 以上）。
2. **以真实状态保真为门槛的轻量化部署验证链。** 不以离线随机状态一致率代替真实验证：正式 FP32 ONNX 模型在真实 SUMO 状态上动作一致率 100%（体积 25.14 KB、单路口推理 0.022 ms），并以实测判定 INT8 量化与结构化剪枝不满足部署门槛——如实记录"理想状态表现好、真实部署失效"的行业痛点现象，形成可复用的轻量化验收方法。
3. **云-边分层双模型架构：边缘毫秒级控制 + 云端慢周期决策。** 边缘 DQN 承担 30 路口 5 秒周期的实时信号控制；云端 LoRA 微调 LLM（事件识别 25% → 99.5% → 部署 100%）承担分钟级交通事件识别与中文管控建议生成，规避 LLM 直接决策的延迟与幻觉风险，填补"边缘实时控制 + 云端慢周期决策支持"分层方案的验证空白。

### 3.1 算法实现细节与训练流程

> 承接第 2.6 节理论设计的工程落地。

#### 3.1.1 实现细节与训练流程

- 环境封装：多路口 RL 环境（660 维观测、30×4 动作、完整回合接口）；单路口训练环境（回合间轮换路口的参数共享包装）。
- 状态提取：返回 660 维浮点数组；车道映射按车道编号首字符判断方向（N/S/E/W），优先直行车道；容错覆盖方向缺失、相位越界、路口不足。
- 网络与训练配置：SB3 DQN，学习率 1e-4，经验回放容量 1,000,000，学习启动 10,000 步，批大小 64，折扣因子 0.99，目标网络更新间隔 10,000 步，探索率 1.0 → 0.05（前 10% 步数衰减）；正式模型 64×64 MLP（约 11,784 参数）+ Double-DQN + 需求门控掩码。快速实验用高性能配置：32×32 网络 + 批大小 1024 + 更高更新频率 + 多环境并行。
- 训练主循环：启动 SUMO → 提取状态切片 → 每路口独立 ε-贪婪选择 → 批量执行（步长 5 s）→ 计算奖励入共享回放池 → 周期网络更新 → ε 衰减。
- 多场景训练：早高峰 / 晚高峰各训练 1,000,000 步（正式模型）；平峰专用模型两次训练均收敛到病态策略（模板 C 的 action_0 占 39%），正式方案采用晚高峰模型泛化——**如实呈现失败案例与应对，是本报告可信度的一部分**。
- 训练性能优化：瓶颈分析（仿真 41.2% + 网络更新 58.8%）→ 极简网络 + 大 batch + 提高更新频率；GPU 实测约 18 steps/s，高性能配置目标 200+ steps/s。
- **图表建议**：训练流程时序图（已有成图）、训练速度对比图。

#### 3.1.2 基线算法实现

- Fixed-Time：读取真实配时方案安装为 SUMO 信号程序，环境步进不做相位覆盖（哨兵动作）——保证"真实定周期基线"而非理想化配时。
- Max-Pressure：选择释放排队压力最大的相位（NS 压力 = queue[N]+queue[S]，EW = queue[E]+queue[W]，理论依据 Varaiya 2013），遵守最小绿灯 15 s。
- Random：随机选相（仅调试/下限参考）。

### 3.2 模型轻量化与云-边-端部署

> 对应功能三赛道 C（AI 模型轻量化部署验证）+ 功能二"平台部署与性能优化"。回答"算法如何以 <1MB、<5ms 的约束落地到边缘，并在云端提供慢周期决策支持"。

#### 3.2.1 边缘 DQN 模型轻量化

- 轻量化链路：SB3 教师（zip ≈121 KB）→ TorchScript → ONNX（opset 17，动态 batch，`(batch,26)→(batch,4)`）→ 体积 25,742 B（约 25.14 KB，较教师减少约 79%）。
- 保真验证（本项目设定的部署门槛）：**真实 SUMO 状态**三场景 × 8 代表路口 × 120 步 = 2,880 条观测，FP32 ONNX 与教师动作一致率 **100%**（不以离线随机状态一致率代替）。
- 性能：单路口 0.022 ms（P95 0.028 ms），30 路口批量 0.029 ms（P95 0.048 ms）——远超 <5 ms 约束。
- 消融与负面发现：
  - 动态 INT8：离线 10,000 条一致率 99.3%，但真实状态一致率降至 84~93% → 判定实验失败，不用于正式部署；
  - 结构化剪枝 + 蒸馏（64×64→56×56 + 30 轮蒸馏）：离线一致率 ~97% → 作为候选保留。
- 结论表述：轻量化手段必须逐任务实测验证（量化/剪枝的"理想路网表现好、真实部署失效"即赛题点名的痛点）。
- **图表建议**：轻量化链路图、推理延迟分布直方图、INT8 真实状态动作不一致示例。

#### 3.2.2 容器化部署

#### 3.2.3 LLM 云脑决策支持（赛道 C）

> 本节对应赛道 C 完整技术链：**数据处理 → 训练/微调 → 模型转换 → 模型部署**；手把手复现流程与部署细节收录于配套教程与部署文档（附录 C 复现清单）。

- **双模型分层架构**：LLM 不参与毫秒级实时控制，承担"城市大脑"慢周期决策支持（2–5 分钟周期），与边缘 DQN 形成云-边分层：

| 层级 | 模型 | 周期 | 职责 |
|------|------|------|------|
| 边缘 | FP32 ONNX DQN（25 KB，0.022 ms/路口） | 5 s | 实时信号控制（30 路口批量） |
| 云端 | 微调 Qwen2.5-0.5B + llama.cpp（f32 GGUF） | 2–5 分钟 | 交通事件识别 + 中文管控建议，供告警与策略干预 |

- 数据处理：SUMO 30 路口真实场景（早/平/晚 + 施工占道扰动）在真实定周期下运行，每 5 s 提取路口特征、30 s 窗口由规则 oracle 标注四类事件（事件 > 溢出 > 拥堵 > 正常）并生成相位感知中文建议；共 136,440 条去重样本，平衡切分 6,531 条。
- 模型微调：Qwen2.5-0.5B-Instruct 基座 + LoRA（r=16, α=32，只训练约 1% 参数），3 epochs，train_loss ≈ 0.025，适配器仅 35 MB；labels 只监督 assistant 段。
- 模型转换与量化适用性验证（负面发现，100 条均衡验证集实测）：

| 模型形态 | 体积 | 事件准确率 | 事件召回 | 单条延迟 |
|---------|------|-----------|---------|---------|
| 基座 bf16（微调前） | ~1 GB | 25.0% | 0% | — |
| 微调后 bf16 | ~1 GB | 99.5% | 100% | ~6.1 s |
| **微调后 f32 GGUF（正式部署）** | **1.98 GB** | **100.0%** | **100%** | **~5.0 s（P95 6.2 s）** |
| Q6_K / Q4_K_M | 506 / 379 MB | 66% / 62% | 4% / 0% | ~3.2 s |

  结论：INT4/INT6/INT8 量化破坏 0.5B 小模型的精细数值判别（事件召回 100% → 0–4%），llama.cpp f16 计算同样损失精度——正式部署必须 f32；对比通用 7B 模型（Q4 后仍 4.5 GB）体积约 1/7，仍满足轻量化叙事。
- 部署与接口：llama.cpp 推理服务（独立进程，端口 8081，OpenAI 兼容，GPU 全层加载，禁用重复惩罚）+ API 云脑分析接口（云脑网关封装）；实现注意：请求不得附加 system 消息（实测加 system 后事件召回归零）。
- 全链路验证：API 网关 → 推理服务 → 微调模型，真实事件样本（J25 北向施工占道）正确返回事件标签与建议，延迟 ~5.6 s。

### 3.3 高保真仿真环境构建

> 对应功能二"高保真仿真验证平台通用性架构搭建"。本节交代承载算法训练与评估的试验场：路网怎么建、信号怎么规范、交通流怎么配置、扰动怎么注入、如何验收。

#### 3.3.1 路网设计与构建

- 规模与拓扑：30 路口 6×5 网格；边界节点为 priority、内部路口为 traffic_light；双向 3 车道、限速 50 km/h（13.89 m/s）；路口间距符合"窄路密网"特征（近距路口，上游排队易回堵）。
- 统一路口顺序：全局配置定义 `J01`–`J30`，SUMO/API/Unity 四层一致。
- 生成与验证流程：netconvert 生成 → 校验 J01–J30 全为 traffic_light、每路口 4 个有效动作、N/S/E/W 映射完整。
- 拓扑模板（本项目的关键发现）：30 个路口存在 **5 种 rl4 相位模板**（A: 20 路口 / B: 4 / C: 3 / D: 2 / E: 1），模板间动作语义不同（如模板 C 的 action_0 仅放右转）。
- **图表建议**：30 路口网格拓扑示意图（标注 J01–J30、边界节点、模板分布着色）。

#### 3.3.2 信号方案规范化与安全优化

- 原始路网相位 1/3 为黄灯 → 规范为每路口 4 个可控相位（最小绿灯 15 s + 黄灯过渡 3 s）。
- 右转/掉头连接改为让行绿灯 `g`，消除 SUMO `Unsafe green` 冲突；复验：1,527 辆到达、平均等待 0.94 s、平均行程 58.60 s、0 碰撞、0 传送。

#### 3.3.3 多时段真实交通流配置

- 三场景均使用 7,200 s 时间窗，需求规模与因子不同：

| 场景 | 车辆数 | 时间窗 | 需求因子 |
|------|-------:|-------:|--------:|
| 早高峰 | 51,868 | 7,200 s | 0.48 |
| 平峰 | 44,947 | 7,200 s | 0.60 |
| 晚高峰 | 50,296 | 7,200 s | 0.42 |

- 需求因子标定方法：按真实定周期基线容量标定（基线 7,200 s 全通、每路口最小绿信比 ≥ 2.0），保证基线"通而不堵"，对比实验在相同负荷下进行。

- **平峰场景**：30 路口全量为负（−1.6%）：低流量路口最小绿灯切换开销（机制性，需改环境重训）；平峰专用模型病态收敛问题尚未根治。
- **评估完整性**：正式四策略 × 30 路口 × 多种子完整对比尚未完成；安全指标同口径统计待补。
- **算法扩展**：邻居状态增强（30 维观测）与 CTDE（QMIX/VDN）对照未实施；LLM 建议 → DQN 掩码闭环干预未做。
- **工程待办**：奖励版本命名未统一（实现 `v3` vs 接口文档 `V5.1`）；容器化需在目标机器实际拉取依赖复验。
- **展望**（按优先级）：平峰 MIN_GREEN/切换惩罚改环境重训 → LLM-掩码闭环 A/B 实验 → V2X 通信延迟模拟 → 结合真实交通数据迁移学习 → 部署至实际边缘设备路测。

### 4.3 结语

- ✍️ 用半页收束：本项目面向雄安"窄路密网"完成了"仿真环境—协同算法—轻量化部署—云端增强"全链条；以需求门控掩码解决了异构拓扑下共享策略的锁死问题，以真实状态保真验证建立了轻量化部署门槛，以 DQN+LLM 分层双模型填补了"边缘实时控制 + 云端慢周期决策"的落地空白；评估体系与接口规范可为地方标准预研提供直接参考。
