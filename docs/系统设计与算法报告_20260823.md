# 雄安新区车路云一体化协同管控系统设计与算法报告

> 版本：2026-08-27（按《系统设计与算法报告框架 v3》重构为 4 章结构）
> 范围：30 路口 SUMO 仿真、共享掩码 DQN、FP32 ONNX 边缘推理、FastAPI/Unity 联调与容器部署、LLM 云脑决策支持。
> 数据原则：本文只引用仓库内可定位的配置、模型、日志和验证报告；尚未取得的"四策略×30路口"完整对比数据不作数值性结论。

## 摘要

面向雄安新区"窄路密网"下路口间相互影响、排队易溢出和多时段交通需求差异的问题，本项目构建了一个覆盖仿真、决策、边缘部署和三维展示的车路云协同管控平台。系统以 30 个可控信号路口为对象，采用"局部观测、参数共享、批量执行"的多路口控制方法：公开状态为 `30 × 22 = 660` 维；单路口在 22 维状态上追加 4 维绝对动作掩码，形成 26 维 DQN 输入；一次控制周期返回并执行 30 个相位动作。正式部署使用与教师 SB3 模型真实 SUMO 状态动作一致率为 100% 的 FP32 ONNX 模型，单路口平均推理约 0.022–0.023 ms、30 路口批量平均推理约 0.029–0.031 ms。三场景评估中，DQN 相对真实 Fixed-Time 配时的 reward 提升在 8 路口代表口径为 +13.7%（早高峰）/ +5.4%（平峰，晚高峰模型泛化）/ +15.4%（晚高峰），30 路口全量口径为 +11.0% / −1.6% / +9.9%，平峰全量负值归因于低流量路口最小绿灯切换开销（详见 3.4.3）。Unity–WebSocket–SUMO–ONNX 已完成三场景闭环记录和 30 分钟稳定性复验。

本文同时补齐容器化设计：SUMO、TraCI、FastAPI 和 ONNX Runtime 在同一可复现运行时镜像中安装；`xiongan-api` 将当前 660 维状态拆分为 30 个局部状态并调用 `xiongan-edge` 批量推理，模型与路网均以只读卷挂载。该设计将模型格式、接口契约和可视化运行链路明确分离，便于后续补充正式四策略全量评估。

面向赛道 C（AI 模型的轻量化部署验证），系统进一步引入 **LLM 云脑决策支持**（3.2.3 节）：以 SUMO 数据工厂 + 规则 oracle 自动生成 13.6 万条"交通状态窗口→事件标签+管控建议"训练样本，LoRA 微调 Qwen2.5-0.5B-Instruct（事件识别准确率从基座的 25% 提升至 99.5%），经 GGUF 转换与 llama.cpp 部署为独立云脑服务（`POST /api/v1/llm/analyze`，实测 100 条验证集准确率 100%，单条延迟约 5 s），与 DQN 边缘实时控制形成"边缘毫秒级控制 + 云端慢周期决策"的双模型分层。量化适用性验证表明：INT4/INT6 量化在 0.5B 小模型上会破坏"事件"精细判别（召回降至 0–4%），正式部署须采用 f32 精度——轻量化手段必须逐任务实测验证。

**关键词：** 车路云协同；自适应信号控制；参数共享 DQN；动作掩码；SUMO；ONNX；Unity；大语言模型；LoRA 微调；GGUF；轻量化验证

## 1. 绪论：项目背景与国内外研究现状

### 1.1 研究背景与赛题需求

雄安新区作为国家智慧城市建设的"未来之城"，其城市肌理以"窄路密网"为特色：路口间距短、路网密度高、机非混行频繁。在高密度路网中，一个路口的放行会改变相邻路口的到达流和排队分布，仅依赖固定配时难以适配早、平、晚高峰的需求变化，排队易溢出并向上游传播。当前"车"的智能与"城"的智慧之间缺乏由 AI 驱动的协同"大脑"，无法对全域交通流进行实时、精准、高效的统筹调控。

赛题（XH-202613）面向雄安新区"城市大脑"建设，提出三大功能需求：

| 功能 | 核心内容 | 本项目的对应章节 |
|------|---------|-----------------|
| 功能一 | 智能交通协同管控算法的抽象设计与建模（场景建模、接口设计、控制策略实现与验证、AI 决策模型） | 3.1（算法设计）、2.3（接口契约） |
| 功能二 | 高保真仿真验证平台通用性架构搭建（≥20 路口路网、数据采集与可视化、算法接入适配器、容器化部署） | 3.3（仿真环境）、2.4（可视化）、3.2.2（容器化） |
| 功能三赛道 C | AI 模型轻量化部署验证（数据处理、训练/微调、模型转换、部署全流程） | 3.2（轻量化与云-边-端部署） |

在产业与政策层面，2024 年 7 月工信部等五部门公布首批 20 个"车路云一体化"应用试点城市，我国智能网联汽车从单车智能迈向"车路云一体化"规模应用新阶段；无锡已完成 1723 个路口信号灯联网联控，深圳、德清等城市落地云控平台与数字孪生应用。本项目以赛题要求为约束，为雄安新区"城市大脑"提供关键技术原型。

### 1.2 国内外研究现状调研

#### 1.2.1 自适应交通信号控制与强化学习方法

传统自适应控制系统（如澳大利亚 SCATS、英国 SCOOT）已在全球与国内城市广泛引进和应用，但以离线优化与经验参数为主，难以适配"窄路密网"高密度、强耦合的路网结构。随着深度强化学习（DRL）的发展，以 DQN（Mnih 等，Nature 2015）为代表的算法被引入信号控制，形成"状态-动作-奖励"建模框架；多智能体强化学习（MARL）的 VDN、QMIX 等值分解方法（CTDE 范式）为区域级信号协同提供了训练思路。

国内研究进展方面，多篇综述系统梳理了该方向：徐东伟等（2022，交通运输工程与信息学报）、华贇等（2023，运筹学学报）、于泽等（2023，计算机科学）、翟子洋等（2024，计算机应用研究）与李泽萱等（2025，价值工程）分别从 DRL 方法分类、MARL 协同、算法类型与智能体类型等维度总结了国内外研究现状，并指出大规模路网协同、真实场景适配仍是开放挑战。代表性算法工作包括：CoLight（图注意力网络建模路口间协同，CIKM 2019，清华）、FRAP（学习相位竞争关系，CIKM 2019）、PressLight/MPLight（压力驱动强化学习，KDD 2019），以及离线强化学习、时空图协同等 2025 年新方向。

**趋势小结**：控制对象从单路口/干道走向区域与路网级协同，MARL 是主流路线；但多数工作在理想化或通用路网上验证，面向真实异构拓扑（本路网实测存在 5 种信号模板）与真实多时段交通流的系统验证仍不足。

#### 1.2.2 车路云一体化与城市级协同管控

国际方面，C-V2X/车路协同示范区与欧洲 C-ITS 部署持续推进，"云-边-端"分层计算架构成为智能交通系统的共识方向：纯云端集中控制面临通信延迟与单点故障风险，纯车端分布式决策无法保障全局最优。

国内方面，2024 年五部门 20 城"车路云一体化"应用试点标志着规模化应用起步；2025 年公开报道显示：无锡已完成 1723 个路口信号灯联网联控，深圳上线交通信息汇聚平台并创新"申报即更新"机制，德清建成数字孪生云控平台并以 AI 算法动态调整信号配时。雄安新区作为"未来之城"，持续开展数字道路建设并落实"窄路密网"规划理念，河北省智能网联汽车标准化技术委员会牵头相关地方标准预研。

**趋势小结**：基础设施层面"车路云一体化"已进入规模化试点，但算法层面的云-边-端混合决策框架公开验证仍少——本项目即面向该缺口，给出"边缘实时控制 + 云端慢周期决策"的双模型分层实现。

#### 1.2.3 大语言模型在智能交通中的应用

大语言模型（LLM）在交通领域的应用近年快速兴起。国际代表性工作包括：LLMLight/LightGPT（首个将 LLM 直接作为信号控制决策智能体的工作）、Traffic-R1（3B 参数信号控制基础模型）、MARLATS（MCP + ReAct 智能体）、GPTTC（LLM 处理偏移左转交叉口）等。国内方面，HeraldLight（ICPADS 2025，北邮）提出双 LLM 架构（LLM-Agent 决策 + LLM-Critic 纠错抑制幻觉），在真实数据集上平均出行时间降低约 20%；苏州"羲和巡路"大模型（2025 年报道）基于大模型 + 标准化联控技术对姑苏区 422 个信控路口分区建模，双向绿波覆盖率达 71.09%，赛事散场 20 分钟清空核心道路，是国内大模型信号控制的落地范例。

**趋势小结**：LLM 从"辅助工具（策略推荐、场景理解）"向"直接决策智能体"演进，并常与 RL 结合形成 actor-critic 或双 LLM 纠错架构；但直接决策面临延迟高、幻觉风险、可解释性要求严苛等落地障碍。"边缘实时控制 + 云端慢周期决策支持"的分层方案尚少被系统验证——本项目即以 DQN 承担毫秒级控制、以微调 LLM 承担分钟级事件识别与建议生成，规避 LLM 直接控制的风险。

#### 1.2.4 交通仿真平台与模型轻量化部署

仿真平台方面，SUMO（德国宇航中心开源，支持 TraCI 在线控制与二次开发）、PTV Vissim（商业）为国际主流；国内清华开源 CityFlow，数字孪生仿真平台亦在兴起。本项目选用 SUMO 作为高保真仿真内核，基于其可编程性构建雄安"窄路密网"特征场景并支持扰动注入。

轻量化部署方面，模型压缩（量化/剪枝/蒸馏）、ONNX 跨框架导出与边缘算力约束下的推理优化是落地关键技术。现有实践多报告离线指标（如随机状态一致率），对"真实运行状态下的保真度"验证不足；小模型上的量化适用性边界亦缺乏逐任务实测——本项目以真实 SUMO 状态动作一致率作为部署门槛，并实测得出 INT4/INT6/INT8 量化破坏 0.5B 模型精细判别的负面结论（见 3.2 节）。

### 1.3 现状评述、待解决挑战与对比分析

综合以上调研，现有工作与本项目的差异可归纳如下：

| 维度 | 现有代表性工作 | 本项目方案 | 差异点 |
|------|---------------|-----------|--------|
| 场景真实性 | 理想/通用路网，同构路口假设 | 30 路口真实路网，实测存在 5 种信号模板（A–E），真实 OD 与配时 | 拓扑异构性被显式建模并治理 |
| 协同机制 | 全局单智能体（维度灾难）或 CTDE（训练复杂） | 参数共享 DQN + 需求门控动作掩码 + 模板分层采样 | 以轻量手段解决共享策略在异构拓扑上的相位锁死问题 |
| 部署验证 | 多停留在算法仿真层 | ONNX 25 KB + 真实状态动作一致率 100% + Docker 容器化 | 以"真实状态保真"而非离线指标作为部署门槛 |
| 云端增强 | LLM 直接决策（延迟/幻觉风险） | DQN 边缘毫秒级控制 + LLM 云端慢周期决策支持 | 规避 LLM 实时控制风险的分层双模型 |

由此引出本项目要解决的三大挑战：

1. **场景真实性挑战**：如何在"窄路密网"、拓扑异构（5 种相位模板）、多时段需求差异下构建高保真、可编程、支持扰动注入的仿真场景（对应功能二）；
2. **协同落地挑战**：如何设计轻量、可扩展、不锁死相位的多路口协同算法，并在 <1 MB、<5 ms 约束下保真部署到边缘（对应功能一、赛道 C）；
3. **评估标准化挑战**：如何建立与真实基线（真实定周期配时）同口径的对比实验与指标集（Mobility/Environment/Safety），为《协同管控系统测试规程》类标准提供参考（对应赛题评估要求）。

**可信度原则**：本文所有结论基于仓库内可定位的配置、模型、日志与验证报告；失败案例与负面发现（offpeak 病态训练、平峰 −1.6%、INT8 量化不可用、LLM 量化破坏召回）如实呈现，不以理想数据替代实测。

### 1.4 问题定义与工程目标

本项目的控制对象为 30 个有信号控制的路口 `J01`–`J30`（6×5 网格，见 3.3.1 节）。在每个离散控制周期（5 s）内，系统为每个路口选择四类相位之一：南北直行、南北左转、东西直行、东西左转。

工程目标及其可验收定义如下。

| 目标 | 可验收定义 | 当前状态 |
|------|-----------|---------|
| 路网规模 | SUMO 与 Unity 均固定识别 `J01`–`J30` 共 30 个路口 | ✅ 30 路口 |
| 状态契约 | 服务端向算法与可视化公开 660 维 `v1-30x22` 状态 | ✅ 稳定 |
| 决策约束 | 30 个路口各 4 个动作；无需求相位由绝对掩码禁止 | ✅ 26 维观测契约 |
| 低时延部署 | 正式 FP32 ONNX 模型小于 1 MB，保持真实状态动作一致性 | ✅ 25.14 KB / 一致率 100% |
| 演示闭环 | Unity 场景切换、SUMO 状态、模型动作、信号灯和车辆刷新可追溯 | ✅ 已验收 |

### 1.5 技术路线与报告结构

技术路线总览：数据与场景（SUMO + 真实配时/OD）→ 算法（共享掩码 DQN + 需求门控）→ 工程化（ONNX 轻量化 + Docker + Unity 可视化）→ 验证（三场景同口径对比 + 轻量化验收）→ 云端增强（LLM 云脑）。系统不将 Unity 当作交通仿真真值来源：SUMO/TraCI 负责交通演化和信号执行；FastAPI 负责会话、状态、约束和接口契约；共享 DQN 或 ONNX 边缘模型负责动作选择；Unity 通过 WebSocket 接收快照并渲染，避免把视觉状态误用于训练或控制。

## 2. 系统总体架构与创新点

### 2.1 云-边-端总体架构与职责边界

| 层级 | 主要组件 | 职责 | 关键输入/输出 |
|---|---|---|---|
| 可视化层 | Unity、`SumoVisualizationBridge.cs`、Dashboard | 路网、车辆、30 盏灯和指标展示；发送场景切换 | WebSocket 快照、REST/WS 场景指令 |
| 管控层 | `server/api_server.py`、`server/visualization_server.py` | 会话、状态校验、动作批量执行、模型登记和错误返回 | 660 维状态、30×4 掩码、30 动作 |
| 仿真层 | SUMO、TraCI、`sumo_files/` | 路网加载、真实交通流、相位执行、检测器统计 | 车道状态、相位、车辆与奖励指标 |
| 边缘推理层 | `edge_deploy/inference_server.py`、ONNX Runtime | 加载正式 ONNX 并做单路口/30 路口批量推理 | `N×22` 状态 + `N×4` 掩码 → `N` 动作 |

### 2.2 一次控制周期与数据流

1. Unity 选择 `real_peak`、`real_offpeak` 或 `real_evening`；服务端启动或重置对应 SUMO 会话。
2. TraCI 读取 30 个路口的局部特征，按固定路口顺序拼接为 660 维状态。
3. 服务端计算每个路口的 4 维绝对动作掩码；22 维状态和掩码供模型组成 26 维观测。
4. ONNX 服务对 30 行观测批量输出 30 个动作；服务端检查动作集合完整、掩码合法和最小绿灯/黄灯约束。
5. TraCI 同一时刻批量下发 `J01`–`J30` 的实际执行动作，推进仿真，随后向 Unity 广播新快照。

![闭环时序](../figures/decision-sequence.png)

这一批量机制避免逐路口推进造成"同一帧内不同路口读取到不同仿真时刻"的不一致。

### 2.3 接口契约设计

基础 API 为 `http://localhost:8000/api/v1`，主要接口为：

| 接口 | 用途 |
|---|---|
| `GET /health` | API、SUMO 可用性与当前会话状态 |
| `POST /simulation/start` | 启动指定真实场景 |
| `GET /simulation/state` | 返回 660 维状态与路口切片 |
| `POST /model/predict` | SB3 模型推理（开发/回归） |
| `POST /edge/predict` | API 调用 ONNX 边缘容器，返回 30 个动作 |
| `POST /simulation/actions` | 校验并批量执行 30 个动作 |
| `GET /edge/health` | 透传检查容器网络内的 ONNX 服务 |

WebSocket 通道为 `ws://localhost:8000/api/v1/ws`，实时推送状态、奖励、掩码与执行动作。错误码体系覆盖：400 `INVALID_ACTION_SET`、409 `STALE_TRANSITION`/`SESSION_BUSY`、422 `LLM_INVALID_EVENT`、502 `LLM_PARSE_FAILED`、503 `SIMULATION_ASSET_INVALID`/`MODEL_NOT_LOADED`/`LLM_SERVICE_UNAVAILABLE`。服务端拒绝缺失路口、非法动作、过期 `transition_id`、缺失 SUMO 资产或不可达边缘服务，均返回结构化错误而非以零值或旧帧继续执行。完整对外契约见 [`docs/接口文档.md`](接口文档.md) 与 [`docs/interface_contract.json`](../docs/interface_contract.json)。

### 2.4 可视化层设计（Unity）

Unity 侧使用 30 路口地图（`xiongan_30.json`）、30 盏信号灯桥接、动态车辆池（支持 64KB 消息分块拼接）和实时指标面板，支持三场景切换。接口边界与已知简化（左转并入直行绿灯显示）见 [`docs/Unity接口边界与30路口资产.md`](Unity接口边界与30路口资产.md) 与 [`docs/Unity基线灯色说明.md`](Unity基线灯色说明.md)。正式闭环联调记录在 [`docs/Unity三场景闭环联调记录_20260821.md`](Unity三场景闭环联调记录_20260821.md)：三场景每帧均为 30 灯、30 动作、30×4 掩码；在正式早高峰模型上的 30 分钟复跑中记录到 1,279 个有效状态快照，协议错误和无快照超时均为 0，动态车辆数范围 400–1,349；服务端主动停止后 Unity 自动重连也已通过记录验证。

### 2.5 创新点与技术亮点

1. **30 路口共享掩码 DQN 契约。** 保持 660 维公开状态可被 Unity 和服务端稳定消费，同时在模型内部采用 22+4 的局部决策契约，避免公共 API 因模型实现变化而破坏。
2. **需求门控动作掩码。** 对不同信号模板按当前需求生成绝对动作掩码，避免无车相位被选中，打断"空相位锁定"的自我强化循环——这是全流程收益最大的单一改进（模板 C 全红误选根治、模板 A 坍缩死锁修复，reward 提升 10%+）。
3. **模板分层采样训练。** 对抗模板不平衡（模板 A 占 20/30）的梯度垄断，少数模板合计采样占比 ≥ 30%（实际 55%），模板 C 双倍加权。
4. **吞吐驱动多目标奖励。** 在排队/等待/溢出/均衡惩罚之上引入通过车辆数与队列减少的正向奖励，让智能体学会"放行更多车辆"而非仅"不扣分"。
5. **可验证的轻量化转换链。** ONNX 导出、模型注册、SHA256 哈希和**真实轨迹**动作一致性验证共同构成部署门槛；不以离线随机状态一致率代替真实状态验证。
6. **云-边分层双模型架构。** 边缘毫秒级 DQN 实时控制 + 云端 LLM 慢周期事件识别与建议生成，规避 LLM 直接决策的延迟与幻觉风险。
7. **闭环可观测性。** 快照中保留 `action_masks`、原始请求动作与实际执行动作，使"模型想做什么""安全约束实际执行什么"可区分、可审计。

- **接口规范**：660 维状态契约、错误码体系与模型注册表（`configs/model_registry.json`）定义清晰、与实现同步，可直接作为《协同管控系统测试规程》类标准的接口参考。

## 3. 算法设计、云-边-端部署、仿真环境与实验验证

### 3.1 协同管控算法设计

#### 3.1.1 多智能体策略选型分析

| 策略 | 核心思想 | 状态空间 | 动作空间 |
|------|---------|---------|---------|
| 全局单智能体 | 一个 DQN 控制所有 30 路口 | 660 维（全局） | 120 维或 30 个独立动作 |
| 独立 DQN（IQL） | 每路口一个独立 DQN | 22 维/路口 | 4 维/路口 |
| CTDE（QMIX/VDN） | 训练时用全局信息，执行时用局部 | 训练 660 维/执行 22 维 | 4 维/路口 |

| 维度 | 全局单智能体 | 独立 DQN | CTDE |
|------|------------|---------|------|
| 训练效率 | ⭐⭐ | ⭐⭐⭐⭐ | ⭐⭐⭐ |
| 可扩展性 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 通信开销 | ⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐ |
| 溢出协同 | ⭐⭐⭐ | ⭐⭐⭐ | ⭐⭐⭐⭐⭐ |
| 推理延迟 | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ | ⭐⭐⭐⭐⭐ |

**选型结论：参数共享 DQN**——沿用独立 DQN 的训练范式（每路口局部观测、局部决策、低通信开销），但 30 个路口共享同一套网络参数与经验回放池，避免为每个路口维护独立参数；网络结构固定，天然支持任意数量路口扩展。其溢出协同通过奖励函数中的高权重溢出惩罚与共享经验回放实现（见 3.1.4）。

#### 3.1.2 DQN 算法核心原理

DQN 用神经网络近似 Q 函数，解决传统 Q 学习的维度灾难，关键技术包括经验回放（打破连续样本的相关性）、目标网络（稳定 TD 目标）与 ε-贪婪探索（平衡探索与利用）。本项目进一步采用 **Double-DQN** 缓解 Q 值过估计。正式模型契约为 `shared-dqn-26x4-v1`：输入 26 维，输出 4 个 Q 值。

对转移 `(s,a,r,s')`，带掩码的 TD 目标写为：

\[
y = r + \gamma (1-d)\max_{a' \in \mathcal{A}(s')} Q_{\theta^-}(s',a')
\]

其中 \(\mathcal{A}(s')\) 是由需求门控掩码给出的合法动作集。优化目标为最小化

\[
\mathcal{L}(\theta)=\mathbb{E}\left[(y-Q_\theta(s,a))^2\right].
\]

训练时 ε-贪婪探索仅从合法动作中采样；在线执行时固定为确定性掩码 `argmax`。

#### 3.1.3 状态-动作-奖励设计

每个路口公开 22 维特征，整个路网状态维度恒为 660，特征划分如下。

| 局部索引 | 特征 | 维度 | 归一化/编码 |
|---:|---|---:|---|
| 0–3 | N/S/E/W 排队长度 | 4 | `min(queue/15, 1)` |
| 4–7 | N/S/E/W 平均等待时间 | 4 | `min(wait/120, 1)` |
| 8–11 | N/S/E/W 车道占有率 | 4 | `[0,1]` 原值 |
| 12–15 | N/S/E/W 溢出风险 | 4 | `min(queue/15, 1)` |
| 16–19 | 当前相位 | 4 | One-Hot |
| 20–21 | 时段特征 | 2 | `sin/cos` 周期编码 |

设计考量：溢出风险特征针对窄路密网"超容"风险，提醒模型优先处理高风险方向；sin/cos 编码解决 23 点与 0 点的周期不连续；相位 One-Hot 让模型感知当前时序状态。

模型不直接把 660 维公共状态送入一个 120 维联合动作头，而是将其拆为 30 个局部状态，每个局部状态再附加 4 位动作掩码，输入尺寸为 `22 + 4 = 26`。掩码为 0 的相位不参与 `argmax`。

![共享掩码 DQN](../figures/shared-dqn.png)

**动作空间**：每路口 4 个可控相位（NS_Straight / NS_Left / EW_Straight / EW_Left），安全约束为最小绿灯 15 s、黄灯过渡 3 s。

**奖励函数**（实现 `REWARD_VERSION = "v3"`，`env/reward_functions.py`）：

\[
r = -\left(0.8\overline q + 0.6 q_{max} + 0.4\overline w + 2.0 p_{overflow} + 0.01 c_{switch} + 0.1 p_{balance} + 0.08 p_{stag}\right)
+ 0.5 r_{queue} + 2.0 n_{crossed} + 0.3 r_{wait}
\]

其中各项含义与权重如下。

| 项 | 权重 | 物理意义 |
|---:|---:|---|
| 平均排队 \( \overline q \) | 0.8 | 通行效率 |
| 最大排队 \( q_{max} \) | 0.6 | 公平性（最堵方向） |
| 平均等待 \( \overline w \) | 0.4 | 通行效率 |
| 溢出风险 \( p_{overflow} \) | 2.0 | 安全性（窄路密网排队回堵） |
| 相位切换 \( c_{switch} \) | 0.01 | 稳定性（低权重，避免压制正常更替） |
| 均衡惩罚 \( p_{balance} \) | 0.1 | 各方向排队方差 |
| 停滞惩罚 \( p_{stag} \) | 0.08 | 死守相位不服务车辆（连续同动作 >2 步） |
| 队列减少 \( r_{queue} \) | 0.5 | 通过车辆数的代理正向奖励 |
| 真实通过数 \( n_{crossed} \) | 2.0 | 本步越过停车线的车辆数（环境层统计） |
| 等待减少 \( r_{wait} \) | 0.3 | 总等待时间减少的正向奖励 |

每个路口独立计算奖励，全局奖励（30 路口平均值）仅用于监控。注意：接口文档历史名"V5.1"与实现中 `REWARD_VERSION = "v3"` 命名尚未完全统一，报告与后续实验以实际运行时输出的 reward version 为准。

#### 3.1.4 参数共享与需求门控掩码设计

**参数共享决策。** 30 个路口共享一套 DQN 参数和经验回放池，而不是维护 30 套独立网络。每个路口仍按自身的 22 维观测和掩码独立选择动作，使不同拓扑模板和不同场景的经验共同更新同一策略。正式网络为两层 64 单元 MLP（约 11,784 参数），输入 26 维、输出 4 个 Q 值。

**模板分层采样。** 30 个路口的 4 动作程序并非同构：路网中存在 5 种 rl4 相位模板（A: 20 路口 / B: 4 / C: 3 / D: 2 / E: 1），模板间动作语义不同（如模板 C 的 action_0 仅放右转）。共享参数 DQN 若按路口均匀采样，模板 A（67%）会主导梯度，把 action_0/3 学成"高价值直行相位"，在模板 C 上 90% 时间误选全红相位。因此训练按模板加权采样（A 0.45 / B 0.15 / C 0.20 / D 0.10 / E 0.10，少数模板合计 ≥ 30%，实际 55%），模板 C 双倍加权；模板分组由 `scripts/validate_network.py --check-templates` 与路网 rl4 状态逐项比对，防路网重生成后漂移。

**需求门控动作掩码。** 相位所服务链路无排队车辆（halting < 阈值 1）时该动作无效；掩码由 `env/global_state.compute_action_mask` 按 rl4 相位状态的绿灯链路动态计算，以最后 4 维追加进观测（22 → 26 维，公开 660 维契约不变）。动机：1M 训练后坍缩会迁移到模板 A（无掩码保护时最后 25 万步 action_0 锁定 93% → 全网死锁），需求门控能打断"空相位锁定"的自我强化循环，故推广到全部模板；全部相位都无需求时（路口空闲）兜底全 1，避免死锁。

**溢出协同机制。** 奖励函数溢出惩罚（权重 2.0）+ 共享经验回放（不同路口经验混合训练，学习通用控制策略）实现路口间间接协同；邻居状态增强（22 维基础状态 + 8 维邻居信息 = 30 维）作为可选扩展列为未来工作。

#### 3.1.5 算法实现细节与训练流程

- **环境封装**：`env/env.py`（`TrafficSignalEnv`：660 维观测、30×4 动作空间、`reset()/step()/_get_state()/_apply_actions()`）、`env/single_intersection_env.py`（`SingleIntersectionEnv`：单路口训练与评估，支持回合轮换路口的参数共享包装）。
- **状态提取**：`get_global_state(num_intersections=30)` 返回 `(660,)` 的 `np.float32` 数组；车道映射取车道 ID 首字符判断方向（N/S/E/W），优先选直行车道（`_0` 结尾）；容错机制覆盖方向缺失、相位越界、路口不足等情况。
- **网络与训练配置**（以 `training/config.py` 为准）：SB3 DQN，学习率 1e-4，经验回放容量 1,000,000，学习启动 10,000 步，批大小 64，γ 0.99，目标网络更新间隔 10,000 步，ε 1.0 → 0.05（前 10% 步数衰减）；正式模型为 64×64 MLP + Double-DQN + 需求门控掩码。快速实验用高性能配置：32×32 极简网络（参数量约为 256×256 的 1/30）+ batch 1024 + train_freq 200 + n_envs=2（SubprocVecEnv）。
- **训练主循环**：启动 SUMO 获取信号灯 ID → 重置并切片 660 维状态 → 每路口独立 ε-贪婪选择动作 → 批量设置 30 路口相位并推进仿真（delta_time = 5 s）→ 计算各路口奖励存入共享回放池 → 每隔 train_freq 步采样更新网络 → ε 线性衰减。
- **多场景训练**：`real_peak` 与 `real_evening` 各训练 1,000,000 步（正式模型）。`real_offpeak` 专用模型两次训练均收敛到病态策略（模板 C 的 action_0 占 39%，归档于 `models/dqn/archive/`），正式方案采用晚高峰模型跨场景泛化——该失败案例如实记录，是评估口径的一部分。
- **训练性能优化**：瓶颈分析（仿真 41.2% + 网络更新 58.8%）驱动下采用极简网络、大 batch 与提高 train_freq 的组合；RTX 2050（4 GB 显存）实测约 18 steps/s（GPU 验证），高性能配置目标 200+ steps/s。

![训练流程](../figures/training-flow.png)

#### 3.1.6 基线算法实现

- **Fixed-Time（真实定周期）**：读取真实配时方案 `data/timing_plans.json` 安装为 SUMO 信号程序（`baselines/fixed_time.py`），`env.step` 不做相位覆盖（哨兵动作 `FIXED_TIME_CONTROL = -1`）——保证"真实定周期基线"而非理想化配时。
- **Max-Pressure 感应控制**：选择能释放最大排队压力的相位（NS 压力 = queue[N] + queue[S]，EW 压力 = queue[E] + queue[W]），遵守最小绿灯 15 s（`baselines/adaptive.py`，理论依据 Varaiya, 2013）。
- **Random**：随机选择相位（0–3），仅作下限参考。
- **算法接入适配器**：`configs/model_registry.json` + `baselines/` 可插拔结构，支持不同算法接入平台运行与测试（呼应功能二"算法接入适配器"要求）。

### 3.2 模型轻量化与云-边-端部署

#### 3.2.1 边缘 DQN 模型轻量化

**轻量化链路**：正式 SB3 教师（zip 约 121 KB）→ TorchScript → ONNX（opset 17，动态 batch，输入 `float32[batch,26]`，输出 `float32[batch,4]`）→ 体积 25,742 B（约 25.14 KB，较教师减少约 79%）。导出与教师权重精确复制，保持 `shared-dqn-26x4-v1` 契约与绝对动作掩码语义（`edge_deploy/`）。

**保真验证（部署门槛）**：以**真实 SUMO 状态**三场景 × 8 代表路口（J01/J05/J10/J15/J20/J21/J25/J30）× 每路口连续 120 个决策状态 = 2,880 条观测进行验证，FP32 ONNX 与教师动作一致率 **100%**（`models/edge/real_state_validation.json`）。不以离线随机状态一致率代替真实状态验证。

**性能**（本机 CPU、ONNX Runtime CPUExecutionProvider、warm-up 后 500 次）：

| 模型 | 单路口 mean | 单路口 P95 | 30 路口批量 mean | 30 路口批量 P95 |
|---|---:|---:|---:|---:|
| peak FP32 ONNX | 0.022 ms | 0.028 ms | 0.029 ms | 0.048 ms |
| evening FP32 ONNX | 0.023 ms | 0.042 ms | 0.031 ms | 0.053 ms |

**消融与负面发现**：
- 动态 INT8（第一隐藏层逐通道动态量化，决策头保持 FP32）：离线 10,000 条状态一致率 99.3%，但真实 SUMO 轨迹上降为 peak 84.38% / evening 93.23% / offpeak（evening 泛化）92.60% → 标记 `experimental_failed_real_state_fidelity`，不用于正式部署；
- 结构化剪枝 + 蒸馏（64×64 → 56×56，物理删除 12.5% 隐藏神经元，按输入/输出 L1 重要度选择保留通道，20,000 条契约化校准状态 + 正式教师 Q 值蒸馏 30 轮）：剪枝 FP32 离线动作一致率约 96.7% → 作为候选/消融产物保留，不替代正式推荐模型。

结论：轻量化手段必须逐任务实测验证——量化/剪枝在"理想状态表现好、真实部署失效"的现象，正是赛题点名的行业痛点（本报告 3.4.4 给出完整验收数据）。详见 [`docs/轻量化验证报告_20260820.md`](轻量化验证报告_20260820.md)。

#### 3.2.3 LLM 云脑决策支持（赛道 C）

> 本节对应赛道 C 的完整技术链：**数据处理 → 模型训练/微调 → 模型转换 → 模型部署**。
> 手把手复现教程见 [`docs/LLM微调手把手教程_20260824.md`](LLM微调手把手教程_20260824.md)，部署细节见 [`docs/LLM部署指南_20260824.md`](LLM部署指南_20260824.md)。

**双模型分层架构**：LLM 不参与实时信号控制（毫秒级响应无法保证、可靠性风险高），而是承担"城市大脑"的慢周期决策支持角色，与 3.1 节的 DQN 形成云-边分层：

| 层级 | 模型 | 周期 | 职责 |
|------|------|------|------|
| 边缘 | FP32 ONNX DQN（25 KB，0.022 ms/路口） | 5 s | 实时信号控制（30 路口批量） |
| 云端 | 微调 Qwen2.5-0.5B + llama.cpp（f32 GGUF） | 每 2–5 分钟 | 交通事件识别 + 中文管控建议，供告警与策略干预 |

**数据处理（数据工厂 + 规则标注）**：SUMO 30 路口真实场景（早/平/晚高峰 + 施工占道扰动）在真实定周期配时下运行，每 5 s 提取路口原始特征（排队辆数/平均等待/占有率/均速/相位），按 30 s 窗口由规则 oracle 自动标注四类事件：**事件（扰动注入真值）> 溢出 > 拥堵 > 正常**，并生成相位感知的中文管控建议。共生成 136,440 条去重样本（`data/llm/dataset_v1.jsonl` + `dataset_incident.jsonl`），按类别平衡抽样 6,531 条（正常/拥堵/溢出各 2000，事件 231 条重复增强）构成微调集（`data/llm/split_balanced.jsonl`）。生成脚本 `scripts/generate_llm_dataset.py`。

**模型微调（LoRA）**：基座 **Qwen2.5-0.5B-Instruct**（约 1 GB，8 GB 显存可训），LoRA（r=16, α=32）只训练约 1% 参数。任务格式：输入路口状态窗口文本，输出 `{"event": "正常|拥堵|溢出|事件", "confidence": 0~1, "advice": "中文建议"}`；labels 只监督 assistant 段（user 段 -100）。训练 3 epochs 后 train_loss ≈ 0.025，适配器仅 35 MB（`models/llm/qwen-traffic-v1/`）。

**模型转换与轻量化验证**：合并 LoRA → GGUF 导出 → 量化对比（100 条均衡验证集，评估脚本 `llm_train/evaluate_gguf.py`，经 llama-server 实测）：

| 模型形态 | 体积 | 事件准确率 | 事件召回 | 单条延迟 |
|---------|------|-----------|---------|---------|
| 基座 bf16（微调前） | ~1 GB | 25.0% | 0%（只会输出"正常"） | — |
| 微调后 bf16（HF 推理） | ~1 GB | 99.5% | 100% | ~6.1 s |
| **微调后 f32 GGUF（正式部署）** | **1.98 GB** | **100.0%** | **100%** | **~5.0 s（P95 6.2 s）** |
| Q6_K | 506 MB | 66.0% | 4% | ~3.2 s |
| Q4_K_M | 379 MB | 62.0% | 0% | ~3.2 s |

**量化适用性结论（有价值的负面发现）**：INT4/INT6/INT8 量化在本任务不可用——0.5B 小模型的"事件"判别依赖"低均速"等精细数值信号，量化后事件召回从 100% 掉到 0–4%；llama.cpp 的 f16 计算同样损失精度（66%），必须 f32 计算。这印证了赛道 C"轻量化部署**验证**"的定位：轻量化手段必须逐任务实测验证，不能无脑压缩。正式部署 f32 GGUF（1.98 GB），对比通用 7B 模型（14 GB+，Q4 后仍 4.5 GB）体积约 1/7，依然满足轻量化叙事。

**模型部署与接口**：
- 推理服务：`tools/llama.cpp/llama-server.exe`（独立进程，端口 8081，OpenAI 兼容接口），启动参数 `--n-gpu-layers 99 --repeat-penalty 1.0`；
- 网关接口：`POST /api/v1/llm/analyze`（`server/llm_service.py`），输入状态窗口文本，返回事件/置信度/建议/延迟；错误码 `LLM_SERVICE_UNAVAILABLE(503)` / `LLM_PARSE_FAILED(502)` / `LLM_INVALID_EVENT(422)` 与既有规范一致；
- 实现注意：请求不得附加 system 消息（微调数据只有 user+assistant 两段，实测加 system 后事件召回归零）；
- 全链路验证：api_server → llama-server → 微调模型，真实事件样本（J25 北向施工占道）正确返回 `{"event": "事件", "advice": "北向检测到施工占道事件…"}`，延迟约 5.6 s（云脑慢周期分析，实时控制仍由 DQN 承担）。

**赛道 C 成果小结**：

| 环节 | 产出 | 关键数字 |
|------|------|---------|
| 数据处理 | 14 万样本 + 平衡切分 | 136,440 条去重，4 类平衡 |
| 训练/微调 | LoRA 适配器 | 准确率 25% → 99.5%，适配器 35 MB |
| 模型转换 | GGUF 对比 | f32 100% vs Q4 62%（量化适用性边界） |
| 模型部署 | llama-server + REST 网关 | 延迟 ~5 s，全链路验证通过 |

#### 3.2.4 双模型分层架构与接口

边缘毫秒级控制（DQN ONNX，3.2.1）+ 云端慢周期决策（LLM，3.2.3）通过统一的 REST 规范接入系统：`/edge/predict` 与 `/api/v1/llm/analyze` 共享同一套错误码体系与鉴权边界，`server/llm_service.py` 作为云脑网关隔离 llama-server 的实现细节。可选扩展（列为展望）：LLM 建议 → DQN 掩码闭环干预（SUMO A/B 对比）。

### 4.2 局限性与未来展望

**局限性**：
1. 平峰场景 30 路口全量为负（−1.6%）：低流量路口最小绿灯切换开销（机制性，需改环境重训）；offpeak 专用模型病态收敛问题尚未根治，当前正式方案为晚高峰模型泛化，不应表述为"平峰专用模型最佳"。
2. 正式四策略 × 30 路口 × 多种子完整对比尚未完成；安全指标（冲突、碰撞、急减速）同口径统计待补。
3. 邻居状态增强（30 维观测）与 CTDE（QMIX/VDN）对照未实施；LLM 建议 → DQN 掩码闭环干预未做。
4. 奖励版本命名未统一（实现 `v3` vs 接口文档 `V5.1`）；容器化代码需在目标机器实际拉取依赖并通过一次 `docker compose up` 的 SUMO/TraCI 联动复验。

**未来展望**（按优先级）：平峰 MIN_GREEN/相位切换惩罚改环境重训 → LLM 建议 → DQN 掩码闭环干预的 SUMO A/B 实验 → V2X 通信延迟模拟 → 结合真实交通数据迁移学习 → 部署至实际边缘设备路测。

### 4.3 结语

本项目面向雄安新区"窄路密网"完成了"仿真环境—协同算法—轻量化部署—云端增强"全链条：以需求门控掩码解决了异构拓扑下共享策略的相位锁死问题，以真实状态保真验证建立了轻量化部署门槛，以 DQN + LLM 分层双模型填补了"边缘实时控制 + 云端慢周期决策"的落地空白；所沉淀的接口规范、评估流程与轻量化判定方法可为地方标准预研提供直接参考。
