## 第 0 章 你要做什么（30 秒看懂）

我们已经有一个**数据工厂**：SUMO 仿真 + 规则标注，产出了 14 万条
"路口的交通状态文本 → 正确答案" 的样本。现在要让一个 **AI 大模型**学会这件事。

模型：**Qwen2.5-0.5B-Instruct**（阿里通义千问 0.5B 版，5 亿参数，约 1GB 文件）。
它本来是个通用聊天模型，我们通过**微调**让它变成交通专家：
输入路口的排队/占有率/速度文本，输出 `{"event": "拥堵", "confidence": 0.9, "advice": "..."}`。

**为什么不用更大的模型？** 赛道 C 的题目是"轻量化部署"。0.5B 模型：
体积 ~1GB（INT4 量化后 ~350MB）、单次分析不到 1 秒、8GB 显存就能训练——
这就是我们答辩要讲的"轻量化"故事。7B 模型（如 Qwen-7B）要 14GB+ 显存才能训练。

## 第 1 章 概念科普（全部用大白话）

### 1.1 大模型是怎么"学会"的？

模型 = 一堆数字（参数），比如 Qwen2.5-0.5B 有 5 亿个数字。
它读入文字，猜下一个字。训练 = 反复给它看"题目+答案"，让它猜，
猜错了就微调数字，下次更准。

- **损失（loss）**：猜错的度量。数字越小 = 猜得越准。训练时你要盯着的就是它。
- **epoch（轮）**：把全部训练数据从头到尾看一遍 = 1 轮。3 轮 = 看 3 遍。
- **batch（批）**：一次同时看多少条。8 = 一次看 8 条再更新一次数字。
- **学习率（learning rate）**：每次更新数字的步子大小。步子太大容易学歪（loss 乱跳），
  太小学得慢。我们用 2e-4（0.0002）。
- **过拟合**：背题背得太死——训练数据全对，换个新题就错。
  对策：训练和验证数据分开，验证集表现变差就说明过拟合了。

### 1.2 LoRA 是什么？为什么我们用它？

直接微调 5 亿参数 = 全量微调，又慢又占显存。
**LoRA** 的思路：不动原来 5 亿个数字，在旁边挂一小块"记忆板"（约 1~5% 的额外数字），
只训练这块板。效果接近全量微调，但：

- 显存占用小（8GB 够用）——因为不用保存 5 亿个数的梯度
- 训练快（我们实测：几分钟一轮）
- 产物小（LoRA 适配器只有几十 MB）——基座模型不用重复保存

训练完的产物叫**适配器（adapter）**。用的时候"基座模型 + 适配器"合体工作。

### 1.3 我们的任务为什么模型学得会？

我们的输出高度模板化（`{"event": "...", "confidence": ..., "advice": "..."}`），
而且类别（正常/拥堵/溢出/事件）和输入文本里的排队数、占有率有明显规律——
0.5B 模型完全学得会，这正是轻量化的前提。

### 1.4 重要：类别不平衡

我们的原始数据里"正常"占 76%，"事件"只占 0.2%。
如果直接训练，模型会偷懒——全部回答"正常"就能蒙对 76%。
**解决办法**：每类等量抽样（每类 2000 条，事件类只有 231 条就重复几遍），
强制模型四类都学会。这一步由 `prepare_data.py` 完成。

## 第 3 章 三步流程

### 第 1 步：准备数据（1 分钟）

```bash
python -m llm_train.prepare_data --samples-per-class 2000
```

做什么：从 14 万条原始数据中按类别等量抽样（每类 2000，事件类重复补齐），
按 9:1 分成训练/验证集，输出 `data/llm/split_balanced.jsonl`。

预期输出：
```
原始样本: 140040  类别分布: {'正常': 106978, '拥堵': 28277, '溢出': 4554, '事件': 231}
输出: data/llm/split_balanced.jsonl  总样本 7478  train=6750 val=728
  正常: train=1800 val=200
  ...
```

### 第 2 步：训练（约 10 分钟）

```bash
python -m llm_train.train --data data/llm/split_balanced.jsonl --out models/llm/qwen-traffic-v1
```

做什么：加载基座模型 → 挂 LoRA → 训练 3 轮 → 保存适配器。
（正式跑之前建议先冒烟：`--epochs 1 --max-train-samples 200` 验证流程，约 1 分钟。）

关键输出（训练日志中）：
- `可训练参数: X.XXM / 总参数 494M (X.X%)` —— LoRA 只训练约 1%
- `'loss': 0.8 → 0.3` 逐行下降 —— 正常；**验证集 loss 回升 = 过拟合**（对策见第 5 章）

产物：`models/llm/qwen-traffic-v1/`（适配器约 20~40MB）+ 中间 checkpoint。

### 第 3 步：评估（约 2 分钟）

```bash
# 微调后
python -m llm_train.evaluate --adapter models/llm/qwen-traffic-v1 --max-samples 200
# 微调前（对比基座，证明微调有效）
python -m llm_train.evaluate --max-samples 200
```

预期输出：
```
JSON 解析率 : 98.5%
事件准确率 : 92.0%
  正常 召回: 95.0% ...
平均单条生成延迟: 120 ms (P95 180 ms)
```

- **JSON 解析率**：模型输出能被解析成合法 JSON 的比例（格式纪律）
- **事件准确率**：类别判对的占比（核心指标）
- **各类召回**：每类别被认出的比例（四类都要高，不能只会说"正常"）
- **延迟**：单条分析耗时（部署时的重要指标）

评估结果存到 `models/llm/qwen-traffic-v1/eval_report.json`。

## 第 4 章 脚本逐行导读（想搞懂原理再看）

### `llm_train/prepare_data.py`

1. `load_samples()`：读两个 JSONL，抽 `text`（输入）/`target`（答案）/`event`（类别），按 id 去重；
2. `build_split()`：按四类分别洗牌抽样（事件不足用 `pool * repeat_incident` 重复增强），
   再按类别分层切成 train:val = 9:1；
3. 输出带 `split` 字段的单文件 JSONL。

### `llm_train/train.py`（核心，5 个步骤）

| 步骤 | 代码 | 说明 |
|------|------|------|
| 1 | `load_split()` | 读训练/验证集 |
| 2 | `AutoTokenizer.from_pretrained` + `AutoModelForCausalLM.from_pretrained` | 加载基座模型（bf16 半精度省显存） |
| 3 | `LoraConfig(r=16, alpha=32, target_modules=[...])` + `get_peft_model` | 挂 LoRA：只训练注意力+MLP 的少量参数 |
| 4 | `tokenize_function()` | 把"题目+答案"编码成数字；**labels 里题目部分填 -100**（不计算损失，只监督答案部分） |
| 5 | `Trainer(...)` | 训练循环、日志、checkpoint 都由框架代管 |

关键参数表：

| 参数 | 默认 | 调大后果 | 调小后果 |
|------|------|---------|---------|
| `--epochs` | 3 | 更可能过拟合 | 学不充分 |
| `--lr` | 2e-4 | loss 乱跳/发散 | 学得慢 |
| `--lora-r` | 16 | 表达力强，易过拟合 | 表达力弱 |
| `--batch-size` | 8 | 吃显存（8GB 上限约 16） | 训练抖动 |

### `llm_train/evaluate.py`

加载模型（可带适配器）→ 逐条生成回答 → `extract_json()` 容错解析
（容忍输出前后杂讯/单引号，解析失败也能抠出 event 字段）→ 统计
解析率/准确率/各类召回/延迟 → 存 `eval_report.json` 并打印 8 条示例。

## 第 5 章 常见问题排查

| 现象 | 原因 | 处理 |
|------|------|------|
| `CUDA out of memory` | batch 太大 | `--batch-size 8` → 4 |
| 训练 loss 不降 | 学习率太小/数据太少 | 冒烟数据训不出效果，属正常；正式数据必降 |
| 验证 loss 训练后期回升 | 过拟合 | 减 `--epochs` 或加 `--max-train-samples` 外的正则（dropout） |
| 模型输出全是"正常" | 类别不平衡没解决 | 确认用了 `prepare_data.py` 的平衡切分 |
| 模型输出 JSON 解析率低 | 生成长度不够 | `--max-new-tokens` 从 160 加到 256 |
| 下载模型超时 | 直连 HF 不通 | `set HF_ENDPOINT=https://hf-mirror.com` |
| torch 报 `no CUDA` | 装了 CPU 版 torch | 按第 2 章命令重装 cu128 版 |

## 第 6 章 步骤③④实测结果（2026-08-24 已完成）

### 6.1 微调效果（100 条均衡验证集）

| 指标 | 基座（微调前） | 微调后 bf16 | 微调后 f32 GGUF（部署） |
|------|--------------|------------|----------------------|
| 事件准确率 | 25.0%（只会说"正常"） | 99.5% | **100.0%** |
| 各类召回 | 正常 100%，其余 0% | 正常100/拥堵98/溢出100/事件100 | 四类全部 100% |
| JSON 解析率 | 100% | 100% | 100% |
| 单条延迟 | — | ~6.1s（transformers） | ~5.0s（llama.cpp GPU） |

### 6.2 量化结论（重要）

Q4_K_M（379MB）/ Q6_K（506MB）量化后准确率掉到 62%/66%，**事件召回 0-4%**——
0.5B 小模型的"事件"判别依赖低均速等精细信号，量化破坏决策边界。
f16 计算同样不行（66%）。**正式部署用 f32 GGUF（1.98GB）**。
这是有价值的负面发现：轻量化必须逐任务验证，不能无脑量化。

### 6.3 部署链路（已验证）

```
LoRA 适配器 (35MB) → merge → HF 权重 → GGUF f32 (1.98GB) → llama-server (GPU, :8081)
                                                              ↓
xiongan-api 网关 /api/v1/llm/analyze ← llama.cpp (OpenAI 兼容) ← Unity/前端
```

- 启动：`tools/llama.cpp/llama-server.exe -m models/llm/gguf/qwen-traffic-f32.gguf
  --n-gpu-layers 99 --port 8081 --alias qwen-traffic --repeat-penalty 1.0`
- 调用：`POST /api/v1/llm/analyze`（body: `{"text": 窗口文本, "junction": "J16"}`）
- 实测响应：`{"event": "事件", "confidence": 1.0, "advice": "北向检测到施工占道事件…", "latency_ms": 5565}`
- 踩坑：**不加 system 消息**（训练数据无 system，加了事件召回掉到 0%）
