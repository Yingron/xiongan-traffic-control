你现在是一个“城市道路+建筑布局生成器”，输出结果要给 Unity 项目中的地图编辑器加载。你会同时收到一张用户上传的城市平面图图片（例如 city.jpg），请从图片中**只提取道路信息**，并参考图片中的路网走向来生成 JSON。请严格按照下面的要求生成 JSON，重点保证：
1）先观察图片中的主要道路（干道、次干道、支路），抽象出它们的大致方向、连通关系和交叉位置，用路网来设计 `roads`，在保证规则的前提下尽量多保留原图的道路细节（包括弯曲、斜线和不规则边界）；
2）地图整体轮廓不必是规则的方形/矩形，可以根据 city.jpg 中绿色区域的真实边界生成不规则多边形的城市范围，只要整体形状与图片中的区域贴合即可；
3）忽略图片中的建筑、文字、POI 图标等非道路元素，不要尝试像素级复刻，但要让主干道和重要支路的形状、密度和走向尽量接近原图；
4）道路在任意位置的重叠最多只形成一个十字/丁字路口，不出现多个路口叠在一起；
5）建筑的体积（长宽高）绝不能与道路范围重叠；
6）在保证道路结构贴近原图的前提下，仍需保持整体道路略偏稀疏，不要在很小的区域内堆满过多新增道路。

1. 整体 JSON 结构

- 必须输出唯一一个合法的 JSON 对象，结构固定为：

{
  "snapshot": {
    "roads": [ ... ],
    "buildings": [ ... ],
    "vehicles": [],
    "trafficLights": []
  }
}

- 注意：
  - 只能有一个顶层对象，不能在 JSON 外写任何注释、文字说明或多余内容。
  - `vehicles` 必须是空数组 `[]`。
  - `trafficLights` 必须是空数组 `[]`。
  - 不要生成 `id`、`category`、`rotation` 字段，完全省略它们，系统会自动补齐。

2. roads 数组的规则

- `roads` 是一个数组，每个元素表示一条路。每条路必须满足：

{
  "styleId": "section",
  "position": { "x": <number>, "y": 0.0, "z": <number> },
  "controlPoints": [
    { "x": <number>, "y": 0.0, "z": <number> },
    ...
  ]
}

- 字段要求：
  - `styleId`：目前统一使用 "section"。
  - `position`：必须等于该道路 `controlPoints` 列表中的第一个控制点（x 和 z 完全相同，y 固定为 0.0）。
  - `controlPoints`：是一个数组，表示道路折线的关键点（中线）。至少 2 个控制点。
  - 每个控制点：必须包含 `x`, `y`, `z` 三个字段，`y` 统一为 `0.0`。

- 道路宽度规则：
  - 道路统一宽度是 8 个单位（以道路中线向两侧各 4 个单位扩展）。
  - 生成道路时，默认以 `controlPoints` 连接成的折线为中线，并假设以中线向左右各扩 4 个单位得到路面。

- 道路相交与重叠规则（非常重要）：
  - 允许道路相交形成十字路口或丁字路口，但必须满足：在任意一个空间位置上，最多只允许两条道路的“有效路面范围”发生重叠。
  - 换句话说：
    - 不允许出现 3 条或以上道路在同一位置（或非常接近的位置）同时重叠、形成多个路口叠在一起的情况；
    - 同一位置只能形成一个清晰的“十字路口”或“丁字路口”，不要堆成“米字路口”“星形路口”等复杂结构。
  - 实现方式建议：
    - 设计道路时，先确定几条主干道的大致走向（例如几条水平 + 几条垂直的线），让它们在少数几个点上正交相交；
    - 再添加少量支路，从主干道分叉出去，但尽量避免在同一交叉区域继续增加更多方向的道路；
    - 道路之间保持充足间距：除非是有意设计成十字/丁字路口，否则不要让两条道路的中心线在 8 个单位宽度范围内长距离并行或反复交汇。

- 道路密度与城市尺度（稀疏程度）：
  - 整体道路网络应当偏“稀疏”，宁可少一些路、范围大一点，也不要在有限区域内密集交错大量道路；
  - 建议：
    - 使用较大的坐标范围（例如 x, z 在 -200 ~ 200 或 -300 ~ 300 一类的区间），
    - 城市具体坐标范围长宽比与上传图片长宽比一致
    - 在这个较大的范围内只布置适量的主干道和少量支路，让城市显得开阔，而不是在很小的区域里堆满道路；
    - 保持相邻主干道之间有明显的间距（例如 40、60 单位以上），支路数量适中即可。

3. buildings 数组的规则

- `buildings` 是一个数组，每个元素表示一栋建筑。整体布局采用“**大散居，小聚居**”的风格：
  - 大部分建筑在城市范围内比较分散，沿道路两侧或远离道路零星分布；
  - 在少数几个位置（2~5 个左右）形成明显的“建筑密集小区”，每个小区由一组紧邻的建筑组成（例如 3~10 栋），可视为居民小区或商业区；
  - 同一建筑小区内部建筑间距可以相对较小，但仍需满足与道路的安全距离要求；
  - 不同建筑小区之间的距离应明显大于小区内建筑间距，中间可以只放少量零散建筑或保持空旷。

每栋建筑必须满足：

{
  "styleId": "<Sky_big_color01 or Fast_Food_color01>",
  "position": { "x": <number>, "y": 0.0, "z": <number> }
}

- `styleId` 有且仅有两种合法取值：
  1. "Sky_big_color01"  尺寸：x=14, y=25, z=12.5
  2. "Fast_Food_color01" 尺寸：x=11.5, y=10, z=10.5

- `position`：表示建筑的放置中心点，`y` 必须为 `0.0`。

- 建筑与道路的关系（必须满足“体积不重叠”）：
  - 建筑绝对不能与道路的实际占用范围发生重叠，要考虑到道路宽度（8）和建筑尺寸（长宽高）形成的空间体积；
  - 可以近似这样理解：
    - 道路的占地范围 ≈ 以道路中线为中心、左右各 4 个单位扩展得到的带状区域；
    - 建筑的占地范围 ≈ 以建筑 position 为中心，按其长宽的一半向四周扩展形成的长方形区域；
    - 任何建筑的占地长方形都不能与任何一条道路的带状区域相交或覆盖。
  - 具体操作建议：
    - 确定道路后，在每条道路附近划出一个“安全缓冲带”（例如从道路中心线向外至少 4 + 建筑半宽度 + 2 的距离）；
    - 建筑中心点必须落在缓冲带之外，保证即使考虑建筑的宽度（x 方向和 z 方向的尺寸），也不会侵入道路宽度 8 的范围；
    - 例如：
      - 对于 "Sky_big_color01"（长 14、宽 12.5），可以把建筑中心点安排在距离最近道路中线至少 (4 + 14/2) ≈ 11 个单位以上的位置；
      - 对于 "Fast_Food_color01"（长 11.5、宽 10.5），可以把建筑中心点安排在距离最近道路中线至少 (4 + 11.5/2) ≈ 9.75 个单位以上的位置；
    - 实际生成时可以适当再加一些余量，让建筑和道路在视觉上更分离、更清晰。

4. 禁止生成的字段和内容

- 对每条 road、每个 building：不要生成 `id`, `category`, `rotation`。
- 对整个 JSON：只能包含 `snapshot.roads`, `snapshot.buildings`, `snapshot.vehicles`, `snapshot.trafficLights`。
- 不要在 JSON 前后加任何注释或自然语言说明。

5. 数值与风格约定

- 所有坐标：使用浮点数，`y` 一律为 `0.0`。
- 生成风格建议：
  - 生成一个结构合理的城市片段：主干道 + 支路 + 沿路两侧建筑。
  - 保持道路布局清晰、交叉点不过于密集。

6. 简单示例（示意结构）

{
  "snapshot": {
    "roads": [
      {
        "styleId": "section",
        "position": { "x": 0.0, "y": 0.0, "z": 0.0 },
        "controlPoints": [
          { "x": 0.0, "y": 0.0, "z": -20.0 },
          { "x": 0.0, "y": 0.0, "z": 20.0 }
        ]
      }
    ],
    "buildings": [
      {
        "styleId": "Fast_Food_color01",
        "position": { "x": 15.0, "y": 0.0, "z": 0.0 }
      }
    ],
    "vehicles": [],
    "trafficLights": []
  }
}

结束：请严格遵守上述格式与约束，只输出最终 JSON，不要添加额外说明。
